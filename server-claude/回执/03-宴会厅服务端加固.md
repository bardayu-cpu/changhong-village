## 1. 读库不漏（分页读全）

**改了什么**：新增 `server-claude/lib/db-page.js`，导出 `fetchAllPages(queryFactory, {orderBy, pageSize, maxTotal})`——固定排序 + `skip` + `limit` 分页读全，每页 100 条（云开发单次 `get()` 的硬上限），读到不满一页为止；`maxTotal` 必传，没传就抛错，防止分页失控，业务代码从 `config.js` 取这个数字。

用它改了这几处（原来都是不写 `limit` 的 `.get()`，超过 100 条会静默截断）：

| 文件 | 原来 | 改成 |
| --- | --- | --- |
| `enterHall/index.js` `loadTables()` | `db.collection('seat').where({table_id:_.neq(BENCH)}).get()` | `fetchAllPages(...)`，排序 `[['_id','asc']]`，上限 `BANQUET_PAGE_MAX_TOTAL` |
| `enterHall/index.js` 进厅提示两条查询 | `toast`/`guestbook` 各一次 `.get()` | 各自 `fetchAllPages(...)`，同上 |
| `enterHall/index.js` 末尾 `allSeats` | `db.collection('seat').get()`（无 where） | `fetchAllPages(...)`，同上 |
| `readBook/index.js` | `orderBy('created_at','asc')` 不设 limit | 见下面单独说 |

`config.js` 新增两个数字：

- `BANQUET_PAGE_MAX_TOTAL: 5000` —— 分页读全的总上限，婚宴量级用不到这么多，纯粹防失控
- `BANQUET_BOOK_READ_MAX: 200` —— readBook 只带回最近多少条，**标「待验证」**，见下

**readBook 单独说**：原来 `orderBy('created_at','asc')` 不设 limit，云开发默认给的是**最老的 100 条**——桌簿写满 100 条之后，新句子反而静默看不见（比"漏读"更糟，等于簿子被锁死在前 100 条）。改成按 `created_at` **倒序**分页取最新 `BANQUET_BOOK_READ_MAX`（200）条，取够了再整体反转回正序返回，`data.lines` 每条的字段结构不变（`{openid, text, at}`）。

**为什么 200 这个数字标"待验证"**：任务卡给的是"最近 200 条"，但没说这是按"总条数"还是"这桌通常能写到多少"来定的，200 是否够用要看实际写簿子的活跃度，我没有依据改，原样按 200 做，请阿鱼/主程认一下。

**这个分页工具放哪**：它做 I/O（依赖调用方传入的云开发查询对象），不是同步纯函数，按 README 约定不放进只放纯函数的 `src/`，新建了 `server-claude/lib/` 目录放它。云函数打包不能 require 文件夹外的代码，所以跟 `src/` 的规则文件一样，由 `scripts/sync-cf-rules.js` 在部署前同步进各云函数自己的 `lib/` 文件夹（只有 `enterHall`、`readBook` 需要，已加进脚本的 `LIB_NEEDS`）；`.gitignore` 加了一行忽略这些生成出来的 `cloudfunctions/*/lib/`；`README.md` 目录说明补了 `lib/db-page.js` 这一行。

**`resident` 按 `_.in` 分 100 个一批查昵称那段**：确认过没问题，**没有动**——这是两个不同的 100 上限：`_.in` 数组本身最多传 100 个 id 是另一条限制，每批传的 id 本来就不超过 100 个，命中的行数天然也不会超过 100，不需要再套一层分页。

## 2. 带回名字（只加字段）

**`enterHall`**：返回的 `names[openid]` 原来是 `{nick, avatar}`，加一个 `inviter`（邀请人 openid，没有就 `null`）。邀请人本人可能没坐在厅里（没换过座、甚至从没进过厅，因此不在 `seat` 表里），所以专门多做一次查询：先按坐在厅里/敬过酒的人查一遍 `names`，再找这批人里"邀请人不在 `names` 里"的那些邀请人 id，单独再查一次，把邀请人的 `{nick, avatar, inviter}` 也放进 `names`。**只找这一层**（names 里已有的人的邀请人），不递归查邀请人的邀请人——蓝图 3.2「看人」卡片只需要显示"XX 带进来的"这一跳，不需要完整链条（这条记进了 `IDEAS.md`，以后如果要看更长的链条需要扩展）。

**`readBook`**：返回的 `data` 加 `names`：写过这些句子的人的 `{nick, avatar}`（这里没有加 `inviter`——任务卡原话就是 `{nick, avatar}`，翻簿子不需要显示"谁带谁进来"，跟 enterHall 的 names 只是**同一套按 openid 做键的约定**，不是每个字段都对齐；如果实际要用起来发现也想要 inviter，请告诉我，加一个字段的事）。`data.lines` 的结构完全没动。

**没有改名、没有改结构**：`godot/回执/席位桥修复.md` 第七节是硬约束——两处改动都只是在已有的 `names`/`data` 对象上加新的键，`me`、`tables`、`bench`、`digest`、`lines` 这些已有字段一个字节都没碰。

## 3. 邀请人只存第一次

依据阶段 1 设计"用谁的链接进来，就长在谁的枝上"。`saveProfile` 收到 `inviter` 时，同时满足才写：这个人 resident 记录还没有 inviter（没有记录也算没有）、inviter 不是自己的 openid、inviter 在 resident 表里存在。不满足**只丢掉 inviter 这一个字段**，其它字段（nick/avatar/gift_value/whisper）照常存、照常返回 `{ok:true}`，不会因为邀请人不对让整次保存失败。

判定逻辑是 `src/resident.js` 新增的纯函数 `canAdoptInviter({existingInviter, selfOpenid, inviter, inviterExists})`，`saveProfile/index.js` 只负责把四个输入准备好（`inviterExists` 需要一次 `db.collection('resident').doc(candidateId).get()`，只有"自己还没邀请人、候选人不是自己"这个前提成立时才会查，省一次不必要的 I/O）。

新增测试 7 条（正常、已有邀请人不再覆盖、填自己、邀请人不存在、候选人是 `null`、候选人是空字符串、已有邀请人是空字符串等同没有），全部在 `test/rules.test.js` 里，跟原来的写法一致（`eq`/`ok` 断言）。

## 4. 超时（没有代码改动，查证过程和结论）

**先说结论**：给 `enterHall`、`readBook` 配成 10 秒这件事，**做不了靠改代码或者本地 CLI**，只能人工去云开发的网页控制台点。我没有代码可以提交，这一条纯粹是调查结论 + 验证步骤。

**查证过程**（没有单纯猜，能查到的都查了）：

1. 微信官方文档（云函数目录结构 / 定时触发器 / 云调用权限几篇）明确写了云函数目录里 `config.json` 支持的字段只有两类：`permissions.openapi`（云调用权限白名单）和 `triggers`（定时触发器）。**没有任何官方资料提到这个本地 `config.json` 支持 timeout 字段**。
2. 本机装的微信开发者工具命令行，我直接跑了一遍 `--help`（只读，没有执行任何部署）：
   ```
   /Applications/wechatwebdevtools.app/Contents/MacOS/cli cloud functions deploy --help
   /Applications/wechatwebdevtools.app/Contents/MacOS/cli cloud functions inc-deploy --help
   ```
   完整参数表分别只有 `--env`、`--names`/`--paths`、`--remote-npm-install`、`--report` 和 `--name`/`--path`、`--file`——**没有任何超时相关的参数**。也就是说用这两条命令部署代码，不会带上任何超时配置，也不会覆盖/重置已经在别处配置好的超时。这跟 README 里"`cli cloud functions` 只有 `list`/`info`/`deploy`/`inc-deploy`/`download`，没有能调用已部署云函数的命令"是同一份 CLI，结论一致，不是我猜的。
3. 微信开放文档里有一个「获取云函数配置」的管理态 API（`api_getfuntionconfig.html`），返回结构里明确写着：
   > timeout: number 函数最长执行时间，单位为秒，可选值范 1-300 秒，默认为 3 秒
   这个"默认 3 秒"跟 HANDOFF 里"`cli cloud functions info` 查到这 6 个业务云函数超时都是默认 3 秒"完全对得上，说明 `cli cloud functions info`（只读）背后查的就是这个"函数配置"，它是独立于代码包（`index.js`/`package.json`/`config.json`）之外的一份服务端配置。
4. 这个「获取/更新云函数配置」的管理态 API **需要 `access_token`**（可以用 `authorizer_access_token`），也就是要拿 AppSecret 换 token，或者走第三方平台授权链路——这两样这个项目都没有，而且 **HANDOFF §0.6 明确"AppSecret 等密钥不要、不存"**，所以这条路径对我来说不可行，我也没有去尝试换 token。

**结论**：timeout 是一份跟代码包分开的"函数配置"，只能通过（a）需要 AppSecret 的管理态 API，或（b）云开发网页控制台的图形界面来改。（a）被 §0.6 挡住，剩下只有（b）。这件事本质上也属于"改小游戏后台设置"，一样要阿鱼先点头（§0.6），跟部署代码是分开的两件事——不会因为重新部署 `enterHall`/`readBook` 的代码而被覆盖或重置（部署命令的参数表里根本不带这个字段）。
