## 0. 阅读规则、版本与证据边界

### 0.1 三个决策

1. 本作重构的是“一封请柬里的连续回忆”，不是保留六种小游戏后补转场。每章的行动、关系推进、请柬变化与下一章入口必须是同一条因果链。
2. 唯一推荐路线：在独立目录建立 **Cocos Creator 3.8 LTS 系列的 2D／2.5D 微信小游戏工程**，重写表现层和剧情编排，复用经审定的数据、素材及服务端领域能力；H5 原样保留为回退原型。补丁版本须在真实微信环境验证后固定。
3. 人物和文字问题必须用统一状态所有权解决：一个人物注册表、一套逻辑画布、一个输入锁、一套文字槽。换引擎只是实现条件，不会自动修复错误素材、错误时间线或重复人物。

### 0.2 权威顺序

当前用户明确确认 > 本文记录的最新冲突决议 > 仍有效的已确认文案 > v1.7／总设计 > 续作提纲在续作范围内的约束 > 历史需求、代码和生成素材。

“文案已定稿”不能阻止用户的新决定覆盖旧句；“素材已在项目中”不等于用户确认其场景真实。未得到资料支持的背景、地点细节、人物、承诺、对白，一律登记待确认，不自行补故事。

## 2. 产品定位与两部作品的关系

### 2.1 一句话定义

朋友打开一封未完成的请柬，借阿鱼的视角重走六段真实回忆；每一次行动使回忆继续、让同一封请柬多完成一部分；最后朋友写下自己的名字，进入婚礼，成为故事未来的一部分。

本作不是普通电子邀请函，不是六款小游戏合集，不是恋爱分支模拟器，也不是《苏七镇奇缘》的提前完整版。

### 2.2 两部作品各自回答什么

| 作品 | 核心问题 | 产品边界 |
| --- | --- | --- |
| 红缘大冒险 | 阿鱼与 Toretto 如何因为一个熟人打开的机会，经过主动联系和选择走到婚礼 | 六段回忆、一封请柬、宾客入席、祝福、席位、续作入口 |
| 苏七镇奇缘 | 婚礼之后，朋友如何进入同一座镇子，并继续连接朋友 | 镇民身份、长期地图生活、黄葛树与关系记录、牵线／许愿等后续系统 |

共同主旨固定为：

> 有人替你开口，缘分才有了开始。  
> 熟人可以打开一扇门，但接不接这根线，始终由本人决定。

阿晓是第一位牵线人，只打开认识的机会，不是月老、系统向导或替两人作决定的撮合成功者。后续关系由阿鱼与 Toretto 自己形成。叙事避免“命中注定”“系统替你匹配”等解释。

### 2.3 微信小游戏目标形态

9:16 手机竖屏，360×640基础逻辑画布，2D角色与2.5D空间层次；原生小游戏入口、引擎场景与UI、平台音频／存储／生命周期。不会使用 WebView 包住原网址。电脑仅作为制作与审核辅助，不替代触控验收。

整体采用相连的紧凑回忆场景，不建立贯通六城的大型无缝地图。首轮先证明上海—成都—来电连续成立，再扩展其他章。

## 3. 玩家身份与不可变事实

### 3.1 三层身份

| 层 | 玩家身份 | 可操作对象 | 强制规则 |
| --- | --- | --- | --- |
| 请柬层 | 屏幕外收到邀请的朋友 | 请柬、翻页等操作 | 不生成宾客小人；帮助阿鱼完成请柬；不代新人署名 |
| 回忆层 | 借阿鱼视角进入过去 | 始终阿鱼，包括她驾驶的车和手边手机 | 不新增现实玩家角色、不操控Toretto、不改写历史；首次明确显示“回忆视角：阿鱼” |
| 婚礼／入口层 | 玩家自己 | 选定的宾客形象 | 六章完成并离开回忆后才写名字、选形象、入席；随后见苏稽镇入口 |

`PlayerContext` 必须显式保存 `invitation | memoryAyu | guest`；`visitorId` 始终同一个，角色控制对象不是登录身份。回忆坐标和宾客坐标分开保存。回忆任务不用“去帮帮她”“请阿鱼搭把手”，不能让操作词重新把玩家与阿鱼分开。旁白仍采用有效定稿第三人称；角色对白中的我／你不改。阿鱼直到终章才越过回忆直接邀请屏幕外玩家。

### 3.2 锁定事实

- 上海先认识阿晓；两人开同款紫色 BMW G42；阿晓说车是哥哥的；两人成为朋友；后来阿晓拉群，把 Toretto 加入；阿鱼在群里认识他。上海初遇没有 Toretto 实体。
- 阿晓：朋友型妹妹、第一位牵线人。允许上海、群聊、普通宾客和未来镇民区；不归入Toretto家庭，不进主人家／亲友主桌，不解释其现实身份来源，不把NPC计为真实已登记宾客。
- 名字始终显示 `Toretto`；兼容旧素材文件名不等于允许旧错拼出现在UI。
- 成都采用有效定稿2024年回成都生活，不取续作讨论稿的2023秋；国企、9点至18点、周末游玩等只使用已有获批文案，不补单位与岗位。
- 来电发生在刚进入Toretto生日当天的深夜；他在电话中说今天是生日；同一天白天阿鱼买一个蛋糕和两束蓝色花；收花在CBD办公室室内。沿用有效事实日期2024-12-04，不再写23点／第二天，不补具体分钟。
- 来电与通话画面只呈现阿鱼房间／手机；Toretto以声音、联系人或电话界面出现。第三章不出现其完整人物立绘；收花采用经确认的办公室桌面近景表达，不让阿鱼突然站到男方办公室。
- 第四章 Toretto 才第一次以完整人物形象站到阿鱼身边。核心动作是阿鱼挪近，随后说“行”；领证日期2025-12-04，地点上海静安区民政局。
- 海南是第一趟夫妻旅行；万宁泳池轻套圈，文昌夜晚看烟花；不把烟花画成火箭发射，不补婚姻重大转折。
- 香港经历真实；界面名称刻意保留“香港大学”，背景允许具有HKUST视觉特征，不自行纠正或还原，不补邮件正文、职位或航班。
- 婚礼进入罗曼山庄；保留有效旧稿的四川乐山家宴背景，不因当前日期晚于婚礼就加倒计时或改变历史。旧请柬“婚礼云餐厅／时间：永恒”的有效可见措辞不由模型自行润色成新地址。
- 作品名《苏七镇奇缘》与地名“苏稽镇”分属两层，不自动统一拼写。

## 4. 连续情感主线、视觉线索与统一循环

### 4.1 唯一情感主线

认识阿晓 → 群聊认识Toretto → 相隔两地但联系未断 → 深夜电话让两人靠近 → 决定成为家人 → 感情进入共同生活 → 面对工作、城市与未来 → 请柬交给真正玩家 → 玩家入席 → 婚礼打开苏七镇入口。

每章设计必须同时回答五件事：关系推进了什么；玩家亲手做了什么；请柬改变了什么；什么物体／声音引出下一章；“熟人打开机会、本人继续选择”的主题如何被感到。任一项缺失，不得只加淡入淡出便视为章间完成。

### 4.2 隐性的“线”

| 场景 | 视觉／声音载体 | 转场动作 |
| --- | --- | --- |
| 请柬→上海 | 空白书写线、道路标线 | 书写线延伸为道路 |
| 上海 | 两辆车、群聊排列与输入光标 | “你好~”光标转笔尖，第一笔落下 |
| 成都 | 墨迹、群消息、手机震动 | 墨迹成为竹林／场景，手机留在叙事中 |
| 房间 | 电话波形、持续联系的已有信息 | 波形成为信纸纹理 |
| 静冈 | 钓鱼线、船绳、挪近的位置 | 信纸白面成为海面；印章圆形成为套圈 |
| 海南 | 套圈轨迹、烟花尾迹 | 最后一朵烟花凝成火漆暖光 |
| 香港 | 邮件边线、行走路径、行李 | Offer界面折成信封，拉远回到请柬 |
| 入口 | 书写、封口、火漆纹理、黄葛树轮廓 | 婚礼后短见枝叶轮廓与一片新叶 |

不加“这就是红线”的解说，不提前说明月老庙、关系枝或匹配规则。以上为象征性游戏表现，不声称真实历史中出现过这些物体变形。

### 4.3 唯一主循环

请柬缺少一部分 → 翻入回忆 → 阿鱼行动 → 完成推进故事的关键动作 → 关系／人生阶段向前 → 情绪落点 → 材料进入同一封请柬并可见改变 → 上一章物体／声音／动作成为下一章入口。

没有“小游戏胜利→领奖页→结算→选章→下一章”主线。没有失败改写婚姻或Offer的分支。轻互动失误只造成短暂动作重试，不丢剧情、不扣情感值。判断某玩法是否保留：换掉人物地点故事后仍完全成立的通用得分关，不能担任本作主线门槛。

## 5. 全篇章节结构

以下“目标”中的新增短操作词是开发用UI草案，不是新增历史对白；正式上线文案需进入Copy表。锁定对白按第6节原样使用，其余有效内容使用C的编号，不擅自补对白。

### 5.1 序章：未完成请柬 → 上海

进入时玩家是屏幕外朋友，画面只有请柬层与已确认当下素材，不出现宾客小人。展示未齐正文与六个待完成部分，不让玩家逐项点空图标。可继续使用A0-1、A0-2、A0-3；其中“帮阿鱼”属于请柬层，合法。

关键操作是打开、翻入回忆。空白书写线延伸为上海道路；进入时明确显示“回忆视角：阿鱼”，身份随后嵌入固定HUD组件，不新增第五个漂浮文字槽。阿鱼的紫色G42沿道路纵深出现，玩家进入驾驶；不再用数层标题卡和“继续”拖延开场。

### 5.2 第一章：上海

| 项目 | 执行定义 |
| --- | --- |
| 请柬缺口 | 缺第一笔／钢笔 |
| 玩家行动 | 驾驶阿鱼的车抵达东方明珠；下车后操控阿鱼走近阿晓；读六句真实对话；观看后来群聊 |
| 关系推进 | 阿鱼先认识阿晓；阿晓后来打开认识Toretto的机会 |
| 互动规则 | 简单点击车道或左右触控；不以换道次数、金币、最长生存作为历史门槛；到达由道路距离与场景入口表达 |
| 场景状态 | 到达后车保持落地位置；阿晓属于世界角色；对话立即锁移动；同名地图角色转立绘时隐藏 |
| 情绪落点 | 群聊停在阿鱼“你好~”；没有额外拉群说明或成功评价 |
| 请柬变化 | 光标变钢笔；在同一请柬写第一笔；`pen.applied=true` |
| 出口 | 第一笔墨迹扩散为成都场景；音乐不断开，不显示领奖／章末页 |

驾驶视觉：统一道路投影、车轮接触面与阴影；车辆从远处沿路来，不从空中落下。景物移动量与路程一致，远景慢、近景快；车速变化有短缓动，不能为赶音乐突然瞬移。现行 `Driving` 与道路投影可参考，但移除“必须换道3次”这种无故事因果硬门槛。碰撞只减速并给短音效，保留恢复宽度。

### 5.3 第二章：成都

请柬缺墨水。场景表现回成都后平静稳定的生活；玩家仍操控阿鱼，而不是直接变成点击熊猫的屏幕外手指。用已有工作／周末旁白引入，不新增单位画面细节。

玩家可接近熊猫完成一次轻投喂；也可以略过投喂，沿可达路线走向下一叙事点。投喂不超过一次主要动作，后续逗留可自由看，不累计6次解锁。熊猫动作和短音效结束后恢复站姿，不以“睡着了才过关”为因果。

同一部手机的群提示必须进入主镜头：已获批文本 `G42在淀山湖 · 有新消息`。玩家点击／靠近查看这一提示，看到与上海相同群名和已知联系人关系；没有获批新消息正文时，只呈现该提示及已知群信息，不伪造私聊或重复播放上海邀请。此动作是理解“远方仍被连接”的必经叙事接点，而不是熊猫成绩触发的Toast。

墨水沿第一笔晕开，为同一张请柬的文字线着色，`ink.applied=true`。手机保持物件身份，场景从成都白天逐渐过渡至12月4日深夜的阿鱼房间；过渡表示跨越时间，不能暗示熊猫基地当天夜里一定发生了电话。最后手机出现 `Toretto 来电`。

**首轮到此停止**：停在来电界面，完成样板检查点保存。不得接听、不得显示接听后的台词、不得送花、不得展开压力段。样板可以显示电话视觉，但接听动作不接入后续剧情；测试构建以调试状态标记终点，不在故事中额外编写“未完待续”对白。

### 5.4 第三章：深夜来电与逐渐靠近（后续范围）

| 项目 | 执行定义 |
| --- | --- |
| 进入 | 从成都保留下来的同一部手机继续，不重新展示选章或重新介绍来电 |
| 必经操作 | 亲手点击接听；在阿鱼房间听Toretto倾诉；继续已确认生日与礼物回忆 |
| 时间 | 刚进入生日当天的深夜来电，同一日白天送蛋糕和两束蓝花；不写23点／第二天 |
| 镜头 | 通话只阿鱼房间／手机；Toretto仅声音或电话UI。办公室礼物只用审定的桌面近景，禁止未确认居家书房和男方完整立绘 |
| 关系推进 | 从普通朋友到更主动分享日常、逐渐亲密并决定在一起；不是玩家改变结果 |
| 压力处理 | 删除75秒三进度条。后续如用短生活蒙太奇，仅串联已有获批信息，表现共同走过，不要求点击三条等时间 |
| 请柬变化 | 电话波形成为信纸纹理；信纸展开承载已积累文字，`paper.applied=true` |
| 出口 | 信纸白面／翻页成为静冈海面 |

有效台词仍按C A3-2a–t中未失效内容执行。A3-1b、A3-2i已因新时间事实失效，不能原样迁；替代措辞在本章开发前确认。不能把同一天送礼与之后逐渐熟悉压成同一天全部完成。不得增写承诺、私聊或未经确认的心理活动。

### 5.5 第四章：静冈与静安（后续范围）

请柬缺印章。海边可进行一次短钓鱼，用来放慢节奏，不做长期胜负。现行一条钓鱼可参考，调整为短等待、短收线、可理解的反馈；不要求技术性失败反复练习。

阿鱼上船，Toretto在本章首次以完整形象站在她身边。用C A4-2a–f的有效对话；镜头中明确留出他身旁位置。玩家必须点击该位置或操控阿鱼挪过去，位置选择只完成已发生的主动靠近，不提供改写婚姻的“拒绝”分支。随后阿鱼说 `行`。

回国过渡后进入领证画面，日期 `2025年12月4日`、地点 `上海静安区民政局` 准确可读。已有插画若人物烘焙，整图作为baked演出，不另叠人物。不得混入旧包“回国某周末另外求婚”的新情节。

印章落下，使请柬第四部分留下印记，`stamp.applied=true`。印章圆轮廓变成海南泳池边的套圈，衔接锁定含义“第一趟以夫妻身份开启的旅行”；不在民政局后领奖。

### 5.6 第五章：海南（后续范围）

请柬缺火漆。玩家以阿鱼身份和Toretto一起做轻套圈；不强制三目标全中，不加独立计分榜、摊主递奖励或未确认兑奖事实。1～2次可理解操作后即可推进；失误有短回弹，不成为主线阻塞。

万宁泳池接文昌夜晚，两人共同看烟花。重点是已成为夫妻后的共同生活，不额外制造转折。保留有效A5文本；烟花画面无火箭发射；baked情侣与sprite二选一。

最后一朵烟花变火漆暖光，生成请柬第五部分的火漆材料／纹理，`wax.applied=true`。这不是最终封死信封；最终装封盖章仍由玩家在终章完成。邮件／信封边线引出香港。

### 5.7 第六章：香港Offer（后续范围）

请柬缺信封。玩家亲手打开Offer邮件，只使用获批标题与文字，名称“香港大学”不改。整理或带上行李作为游戏操作表达，不补真实航班、搬家人物或额外邮件正文。随后操控阿鱼走过香港场景，行李随角色一起移动，走向可达出口。

删除接10个掉落祝福／金币的关卡与左右接物HUD。若需庆祝，只用几秒非写实转场，不要求收集，且低动态选项可跳过效果但不跳剧情。

### 5.8 终章：玩家入席、婚礼与苏七镇入口

阿鱼第一次越过回忆直接邀请玩家，使用有效A7文案。进入罗曼山庄婚礼，留祝福、获得席位；姓名／形象／席位由服务端确认并可跨设备恢复。普通祝福与悄悄话分开处理，默认不因旧控件存在就扩大公开范围。

婚礼叙事完成后才出现去苏稽镇的入口；短暂看见黄葛树轮廓和一片新叶，不展示完整树、不宣告已分配镇民身份。点击入口可记录 `townEntryOpened`；镇民、叶子归属、“你在这儿／由谁带进来”的记录由续作生成。

## 7. 人物渲染与场景事实规则

### 7.1 素材清单先于渲染

每张背景登记：`assetId`、来源、确认状态、真实地点／时间、`bakedActors`、烘焙文字、逻辑裁切框、地面线、可行走区、遮挡层、许可用途。状态仅可为 `approvedEmpty | approvedBaked | needsConfirmation | rejectedForScene`。

原则上使用空场景。背景中存在人物，必须标baked，不再叠同名角色；不确定人物是不是主角时不能自行判断为安全空景。保留原素材文件与“从新版主线停用其引用”是两件事，本轮不删图。

### 7.2 每句完整状态，不继承残留

每句／旁白／演出节点都必须显式提供：

```ts
type Shot = {
  id: string;
  sceneId: string;
  speaker: 'ayu' | 'axiao' | 'toretto' | 'narrator' | 'system';
  copyId: string;
  actorMode: 'sprite' | 'baked' | 'none';
  actorSlot: 'left' | 'right' | 'center' | null;
  background: string;             // 不能省略后沿用上一句
  visibleActors: ActorShot[];     // 每人自己的mode/slot；无人物显式[]
  hiddenWorldActors: string[];
  inputPolicy: 'locked';
  phonePresentation: string | null;
};
```

顶层`actorMode`／`actorSlot`专指本句`speaker`的呈现方式；镜头内其他人物必须在`visibleActors`逐人显式声明自己的mode／slot。说话人有可见形象时，两处声明须一致并指向同一个实例，不能据此各创建一次。

`none`仅用于明确没有人物图像的旁白、系统字幕、纯电话声音，不是偷漏演员的降级方式；有独立立绘必须sprite，背景已有角色必须baked。电话联系人头像属于Phone层，不得借none再叠同人全身。场景编译时校验所有字段、背景存在、角色出场许可。

渲染提交必须原子执行：获取输入锁→清输入／路径→验证新镜头→隐藏旧演员与同名世界角色→应用完整新背景／演员／字幕→显示新镜头。不能先换人物、等下一帧才隐藏背景内同人，也不能淡变时留下两份同一人物。

### 7.3 单实例约束

ActorRegistry按`sceneId + actorId`管理可见归属；来源可为world、dialogueSprite、bakedBackground、phoneAvatar。每镜头列出必须可见和禁止可见的角色：必须出现者每人恰好1个，禁止出现者为0；并且任何同人最多1个视觉实例。纯旁白不强迫所有故事人物各出现一次。

逐句截图时，烘焙人物也计数，不只统计节点数量；电话画面若已显示某人头像，就不同时显示其同名立绘。上海Toretto只能有一个联系人头像，上海现实镜头为0；第三章无完整Toretto；第四章才首次两人完整同框。多人对话可同时保留当前镜头批准的两位演员，但世界同名角色仍隐藏，其他NPC、任务标签不可抢占画面。

对话结束后释放本次锁，恢复原世界坐标／朝向／姿态，清空旧触控向量；只有玩家重新输入才移动。不能恢复旧寻路后突然跑走或瞬移。

## 8. 统一画布、HUD、字幕与2.5D视觉

### 8.1 360×640逻辑布局

| 区域／锚点 | 逻辑坐标 | 规则 |
| --- | --- | --- |
| HUD | y=0–64 | 章节名中央固定；暂停／声音避微信胶囊；身份提示归此组件 |
| 当前目标 | y=64–116 | 同时一条，最多两行 |
| 人物表演区 | y=64–456 | 核心脸部与动作不被UI遮住 |
| 对话区 | y=440–624 | 底部固定；440–456为有意重叠边缘，不能遮脸 |
| 全身人物脚底 | y=456 | 同一地面锚点，不以图片外框底部代替脚底 |
| 左／右槽 | x≈96／264 | 依据透明内容范围等比缩放，不能分别按屏幕高宽拉伸 |
| 底部缓冲 | y=624–640 | 再叠加设备安全区；摇杆不可压系统手势区域 |

先取设备安全矩形并扣除胶囊避让区，计算 `s=min(safeWidth/360,safeHeight/640)`；逻辑画布整体居中，使用同一平移与缩放矩阵。输入点用逆矩阵映回逻辑坐标；DPR仅决定渲染精度，不改变命中范围。额外屏幕区域可延展背景，不把HUD／人物按各自百分比摆放。

### 8.2 仅四个固定文字槽

| 信息 | 位置与容量 | 所有权 |
| --- | --- | --- |
| 章节名 | HUD中央，固定 | ChapterHUD |
| 当前目标 | HUD下，≤2行、同时1条 | ObjectiveSlot |
| 对话／旁白／过场 | 底部固定区域 | DialogueSlot |
| 系统通知 | HUD下临时浮层，排队逐条 | NotificationQueue |

通知显示时暂让目标槽避让／隐藏，不能覆盖成两层阅读。物体标签仅允许2～5字，如“喂一下”“坐这里”“上车”，不承载完整叙事；该类是物件操作标识，不扩展为第五套叙事字幕。

所有文字淡入180～250ms，上移≤6px；无长距离飞行；同一copyId同屏不得出现两处；通知切场清空。对话出现：隐藏目标、摇杆、物件标签和操作文字，停止移动，保留章节名，只展示该镜头当前演员与底部对话。菜单、加载、错误是模态状态，不与四槽争抢常驻位置。

### 8.3 2.5D视觉规范

- 保留已确认Q版人物与高精度16-bit像素方向；不是写实3D化。空背景、可行走地面、人物、前景遮挡分层。
- 用脚底y排序表现前后；碰撞以地面脚印而非人物头部矩形；前景遮挡不能覆盖全部返回路径。
- 角色／车有接触阴影；影子随地面而非图片中心漂浮。远近尺度服从同一投影，不同时使用无关缩放规则。
- 一个镜头确定地平线、光向、人物尺度和可交互区域。背景的戏剧化光线不能遮住目标和脚底。
- 摄像机只服务当前行动和情绪落点；移动时保留下一步路径，镜头不能把玩家推入UI遮挡区。非必要抖动关闭；低动态模式保留信息、减少位移效果。
- 不为“更丰富”补地标、办公室、群众或装饰当真实经历。先验一张代表性场景的人物、地面、遮挡、字幕，再扩素材家族。

## 9. 操作、移动、暂停与重玩

### 9.1 五种共用操作

移动、靠近、点击、按住、选择位置。所有输入转成同一Intent，UI不直接改物理坐标。点击地面与摇杆不能同时争夺目标；摇杆开始取消点击路径；交互只选最近合法对象，不穿墙触发。

实际位置更新→计算本帧位移→更新朝向与步态→脚底排序→渲染。步态按走过距离推进；碰撞阻挡时不原地滑步；停下≤300ms返回站立帧。长帧限制delta／固定步进，不允许退后台后一帧走过整个地图。

对话、电话、聊天、过场、暂停各自持有输入锁；所有锁释放才允许移动。触控end／cancel、失焦、后台时清零；恢复不沿用按住状态。所有可达点应能返回，若门在剧情中关闭，须先保证玩家在正确区域且保留返回／明确场景出口，不产生单向死区。

### 9.2 暂停与重玩

暂停冻结世界、对白打字、聊天定时、转场时钟、音频；保存稳定检查点。恢复不跳句、不自动接听、不重发奖励。

菜单保留继续、本章重玩、重新开始游戏、回忆册、声音。首次主线不自动打开菜单／回忆册。“本章重玩”为独立replay状态，保留主线已完成材料与现实身份；“重新开始游戏”为新回忆runId，保留稳定visitor、已登记宾客、席位与祝福。若用户确要删除个人数据，另设有明确对象与后果的删除流程，不能藏在重玩按钮里。

回访优先继续未完成检查点；全通后可入席／回忆册／已打开的续作入口。回放历史不新增两游戏身份、不重复生成叶子或奖励。

## 10. 音乐与声音

一个核心旋律贯穿，全篇按城市与情绪变奏；一个MusicDirector持有BGM，场景只请求情绪／编配变化，不自行创建播放器。现有旋律结构可参考；正式声音素材是否重用先审听，不以代码存在代替听感验收。

默认静音或遵守玩家上次选择；首次有效触控后才按选择启用声音。对话时自动压低背景音乐，结束平滑恢复；不在每句／每次render重启。跨章共用相位或短交叉淡变，实际速度与驾驶／轻互动节奏协调。

音效范围：电话、群消息、车、脚步、印章、火漆、烟花；音量克制、同事件幂等。脚步与步态接触帧触发，不按timer无位移乱响。后台暂停，回来保持静音选择并恢复当前位置；电话界面重进不得多层铃声叠加。失败加载可静音继续但明确可恢复，不能因音频资源失败阻塞回忆。

测试包含：静音开关覆盖BGM和SFX、对话ducking、跨章不中断、前后台不重复启动、耳机／系统中断恢复、快速连点不爆音。当前未实际完成耳机与真机听感验收。

## 11. 同一封请柬与六件材料

材料属于请柬层的象征性回忆收藏，不新增“阿晓送钢笔”“捡到丢失印章”等史实。每次获得必须改变同一个Invitation模型与画面，不另发奖励卡。

| 章 | 材料 | 即时可见变化 | 持久状态 | 终章用途 |
| --- | --- | --- | --- | --- |
| 上海 | 钢笔 | 光标变笔尖，第一笔落下 | pen.acquired/applied | 完成玩家署名动作 |
| 成都 | 墨水 | 已有线条着色／晕染 | ink.acquired/applied | 书写所用墨迹 |
| 来电 | 信纸 | 电话纹理铺展为正文纸面 | paper.acquired/applied | 承载请柬正文 |
| 静冈／静安 | 印章 | 请柬留下第四部分印记 | stamp.acquired/applied | 最终盖章工具／纹理 |
| 海南 | 火漆 | 暖光凝为火漆材料与纹理 | wax.acquired/applied | 装封后最终封口 |
| 香港 | 信封 | 邮件折为信封，六页归位 | envelope.acquired/applied | 容纳已完成请柬 |

事件以`runId + chapterId + materialId`幂等。提交`acquired`和`applied`须保证崩溃恢复可重放视觉而不重复写入：先保存待应用事件，执行短演出，确认应用；重进根据事件状态补完或恢复，不发第二件。用户主动回看不改变完成历史。

终章状态为`readyToWrite → named → avatarSelected → assembled → enveloped → sealed → delivered → seated`。前五章出现的火漆纹理不等于终章已sealed；第六章信封出现不等于已替玩家写名。

## 12. 状态机与模块契约

建议不是把旧HTML逐页翻译成Prefab，而是重新建立如下所有权：

| 模块 | 唯一拥有的状态 | 其他模块如何使用 |
| --- | --- | --- |
| JourneyMachine | 章节、节点、三层身份、下一节点 | 只接合法Intent／领域事件，不从UI读剧情状态 |
| SceneDirector | 当前sceneId、镜头完整快照、转场 | 创建／卸载场景，取消旧scope异步任务 |
| ActorRegistry | 同人视觉实例、world↔sprite↔baked归属 | 镜头提交前验证，不由对白组件私自加人 |
| InputService | 触控意图、路径、按住、锁集合 | 世界／UI共享意图；锁定时全部清零 |
| Dialogue／ChatPlayback | copyId、句序、消息序、播放时钟 | 完成事件推进Journey；不自行发材料 |
| TextSlots | 章节、目标、对白、通知唯一位置 | 显示投影，不复制游戏规则 |
| InvitationComposer | 六部件、应用事件、装封／盖章 | 章节只发一次应用请求 |
| SaveService | schemaVersion、runId、checkpoint、同步队列 | 本地与云端版本化，不比较章节数量后粗暴覆盖 |
| AudioDirector | 单BGM、SFX、静音、ducking、后台状态 | 使用事件ID防重播 |
| PlatformAdapter | 微信登录、存储、网络、窗口、生命周期 | 领域逻辑不引用wx／DOM |
| GuestService | 现实宾客、席位、祝福、入口交接 | 服务端权威，不受回忆重玩重置 |

首轮Journey节点必须可单元测试：`invitation_open → shanghai_drive → shanghai_arrive → approach_axiao → meeting → later_caption → group_chat → pen_applied → chengdu_arrive → chengdu_life → group_notice_seen → ink_applied → day_to_night → incoming_call`。

剧情节点都有稳定ID、输入许可、进入条件、退出条件、保存点、可见演员集合、背景审核状态。所有异步回调捕获sceneScope；离开后取消，不让旧定时器在下一章写字幕或发奖励。

## 13. 存档、身份、宾客与两游戏数据

### 13.1 新存档最小结构

```ts
type MemorySave = {
  schemaVersion: 18;
  contentVersion: string;
  visitorId: string;        // 服务端权威，不是角色ID
  runId: string;
  revision: number;
  context: 'invitation' | 'memoryAyu' | 'guest';
  chapterId: string;
  nodeId: string;
  checkpoint: { sceneId: string; position: Point | null; facing: string | null };
  dialogue: { copyId: string | null; completed: boolean };
  chat: { messageId: string | null; completedIds: string[] };
  completedChapters: string[];
  invitation: InvitationState;
  pendingEventIds: string[];
  preferences: { muted: boolean; reducedMotion: boolean };
};
```

保存稳定节点与完整句状态，不保存每个打字字符或未完成物理轨迹。聊天保存最后已展示消息；恢复该消息完整可读，再继续剩余队列。保存触发：关键行动、材料应用、场景转换、后台、暂停；不逐帧写存储。

本地可先玩；离线写队列，联网按服务端revision与幂等ID同步。不能“通关章数更多者获胜”后丢同进度姓名／封口变化。恢复时校验contentVersion；旧检查点无对应节点则回最近安全节点并保留已完成部件，不猜测到错误背景。不同run不互相覆写。现行已有6位恢复码（`L/server/recovery.js:25–60`），不能误报“完全没有跨设备恢复”；其进程内防猜限流（`:5,9–22`）与Cookie恢复方式须重新评估，不能直接扩为长期社交身份方案。

### 13.2 微信身份映射

服务端用微信登录code换取身份，维护 `(appId, openId) → visitorId`；unionId只有满足条件时可用，不能假定必有，也不能假定两款小游戏不同AppID的openId相同。session_key与应用密钥只留服务端，不进入客户端包、分享参数或日志。

现有网页Cookie不能直接当小游戏登录方案。H5绑定到小游戏必须通过有期限、一次性、服务端验证的绑定凭据；不能凭昵称、可猜恢复码或客户端自报visitorId合并。旧恢复码只作为待安全评估的兼容入口，不默认变成跨游戏身份凭证。

### 13.3 最小交接契约

| 字段 | 红缘负责 | 苏七收到后才负责 |
| --- | --- | --- |
| stableVisitorId | 稳定记录／映射 | 建镇内身份关联 |
| wechatIdentityMapping | 服务端平台身份映射引用 | 经授权解析本游戏身份，不暴露其他App原始凭据 |

## 14. 微信小游戏迁移评估与唯一选型

### 14.1 官方核验边界

检索日2026-09-10。微信开发者文档主站的若干小游戏指南在当前检索环境不可打开，不能宣称“最新微信官网要求已全量核验”。本次使用微信官方组织发布的小游戏API声明源码和Cocos／Phaser官方文档作为可核实一手依据；分包额度、后台资质与域名配置必须在开工／提审时再通过真实AppID和开发者工具验证。

微信官方 [minigame-api-typings](https://github.com/wechat-miniprogram/minigame-api-typings) 说明API声明由官方文档生成；[CHANGELOG](https://github.com/wechat-miniprogram/minigame-api-typings/blob/master/CHANGELOG.md) 最新可见2026-07-27 v3.8.21，定义更新至3.17.0。这是声明版本，不是要求本项目最低基础库强行设3.17.0。

### 14.2 三路线真实比较

| 维度 | 继续适配当前Phaser | 原生微信Canvas重写 | Cocos Creator 2D／2.5D |
| --- | --- | --- | --- |
| 现有代码复用 | Phaser部分可参考，但上海是自写Canvas，后续大量DOM仍要重写 | 纯规则／素材可复用，渲染基础设施自建 | 纯规则／素材／后端可复用，场景UI重建 |
| UI一致性 | 仍需专门统一节点、文字、输入，不可保留DOM混搭 | 可统一，但文字布局、命中、动画、层次都自己维护 | 统一Scene／Prefab／Sprite／Label与安全区，适合固定图层 |
| 微信平台 | 必须验证当前Phaser与适配器、资源、音频、生命周期兼容 | 直接接wx，但所有公共能力自己包 | 有官方微信发布与引擎适配链路；登录等业务SDK仍自己接 |
| 2.5D与编辑 | 有能力，但当前两种渲染器仍需合并 | 能实现，编辑与调试工具成本高 | 节点层次、图集、动画、相机、资源Bundle利于维护 |
| 续作长期地图 | 可做，需补地图资源／社交架构 | 长期扩展基础设施负担最大 | 表现层可支持地图扩展，社交与持久权限仍服务端负责 |
| 性能风险 | 适配层、两套循环、DOM遗留、资源加载不一致 | 小样轻，后期易积累排版／排序／资源释放成本 | 引擎基础包与节点开销须裁剪、合批和实测，不能假定更快 |
| 维护风险 | 旧规则迁移冲动强，适配与故事重构同时进行 | 维护自研小引擎，人员交接成本高 | 一次性迁移成本中高，但平台与视觉工具链较完整 |
| 本项目结论 | 可行，不推荐作为主路线 | 可做样板，不推荐长期主路线 | **唯一推荐** |

Phaser官方定位浏览器优先，不等于“Phaser绝对不能上微信”；不推荐的原因是当前整套UI与叙事本就要重构，保留旧表现层节省有限。[Phaser官方说明](https://docs.phaser.io/phaser/getting-started/what-is-phaser)

Cocos官方提供微信小游戏构建与平台适配，同时明确小游戏不是浏览器、不支持WebView，远端不可下载脚本；这支持独立工程而非包装网址。[Cocos微信发布](https://docs.cocos.com/creator/3.8/manual/zh/editor/publish/publish-wechatgame.html)

### 14.3 平台检查清单与实施动作

| 检查项 | 当前H5风险 | 微信实现／验收动作 |
| --- | --- | --- |
| HTML入口 | 多HTML跨路由，第一章与后续分离 | 一个小游戏入口与Journey根场景；不搬网页导航 |
| CSS／DOM对话 | innerHTML、百分比、DOM表单、Canvas混排 | 引擎UI重写；共用SafeViewport与文字槽 |
| Canvas／Phaser | 上海自绘Canvas＋后续Phaser按章建毁 | 一套引擎循环；领域逻辑不依赖浏览器全局 |
| 图片 | 现行assets目录约37MiB磁盘占用，含生成原图与优化版，不等于正式包大小 | 逐图审核、只打包引用资源、图集／压缩、分章预载释放；测解码后的纹理内存 |
| 音频 | 两套音频控制、浏览器AudioContext | 一个AudioDirector＋平台适配；长BGM与短SFX分组，真机后台／静音验收 |
| 本地存档 | 多localStorage键和版本 | wx存储适配、单一schema、checkpoint；不当可靠永久数据库 |
| 网络存档 | fetch＋Cookie识别、章数合并 | wx.request＋服务端会话、revision、幂等、离线队列 |
| 用户身份 | 浏览器匿名ID与恢复码 | wx.login→服务端映射；跨AppID和H5绑定单独设计 |
| 宾客 | 形象只本地；名字／公开祝福控件与后端不一致 | 服务端avatarId与可见性；席位幂等；拒绝非必要授权仍可玩回忆 |
| 云婚宴接口 | 已有登记／列表／祝福业务，但无完整前传→续作契约 | 保留领域能力；减少长期社交；新增授权交接，不在客户端拼身份 |
| 触控 | pointer/keyboard、各场景控制不同 | 引擎统一触控Intent；end/cancel/后台清零；逻辑坐标逆变换 |
| 生命周期 | document.hidden只局部处理 | onHide暂停时钟与声音并存检查点；onShow校验会话、窗口与资源，不自动接听 |
| 分包 | 旧build复制整个public，容易带原图／不用脚本 | 开场最小包；按章节Bundle；JS合法分包，媒体可远程；预载下一场、释放上一場 |
| 扩展 | 前院原型并非长期地图引擎 | 共用身份／存储／输入契约；后续苏七单独场景包及服务，首轮不开发镇玩法 |

微信官方声明确认Canvas／Image、touch start/move/end/cancel、onHide/onShow、login、request、SocketTask、InnerAudio等API；`getWindowInfo`含safeArea，声明要求基础库2.25.3；存储注释为单key1MB、总10MB，且可能被清理。项目需按实际采用API设最低基础库并做能力检测，不因类型可编译就视为真机可用。[微信官方API源码](https://github.com/wechat-miniprogram/minigame-api-typings/raw/refs/heads/master/types/wx/lib.wx.api.d.ts)

分包额度：当前Cocos 3.8文档记载主包≤4M、分包合计≤30M、单分包不限制大小；这是引擎官方当前记载，**尚未通过微信本源页面／项目后台二次核验，不作为已核准额度承诺**。不能套用普通小程序的2M／20M。启动前提交真实构建包报告，记录工具、基础库、AppID环境和当前规则。[Cocos小游戏分包](https://docs.cocos.com/creator/3.8/manual/zh/editor/publish/subpackage.html)

资源Bundle与平台分包不同；小游戏分包不能直接配置为远程包。远程仅供允许的图片／音频等资源，不能下载JS作为热更新。按资源hash版本缓存，下载失败保留过渡画面并可重试。[Asset Bundle](https://docs.cocos.com/creator/3.8/manual/zh/asset/bundle.html)

SafeArea组件可辅助，但还要实际避胶囊、刘海与底部手势区域；合批受纹理、材质、层次与遮罩影响。首轮限定图集／节点／遮罩数量，记录实测，不以引擎选择代替性能预算。[SafeArea](https://docs.cocos.com/creator/3.8/manual/zh/ui-system/components/editor/safearea.html)、[2D合批](https://docs.cocos.com/creator/3.8/manual/zh/ui-system/components/engine/ui-batch.html)

iOS普通／高性能模式分别测试；不把官方文档中的历史设备内存数字当今日统一红线。记录峰值纹理、音频与JS内存、首次进入和多次回访曲线，确认无持续增长。[微信iOS优化](https://docs.cocos.com/creator/3.8/manual/zh/editor/publish/wechat-ios-optimize.html)

隐私：只收任务必要昵称、形象、祝福；按功能与后台配置接授权流程，不在开场索要通讯录、位置、真实头像。`requirePrivacyAuthorize`是可选辅助API，不是每次启动必须弹出的所有权限请求。具体提审申报与域名合法性由真实项目环境核验。

音频中断独立于一般后台切换处理；收到中断结束事件后，再按用户静音选择恢复。监听内存警告，卸载非当前章资源；不能拿强制GC代替资源管理。`safeArea`未返回时回退完整窗口，再按可用系统信息安全避让。WebP在实际目标基础库与iOS／安卓的解码需要真机验证，不能仅凭浏览器可显示就承诺全部兼容。短SFX和长BGM分别选平台支持格式与实现，避免将高内存WebAudio路径不加评估用于长音频。[微信官方API源码](https://github.com/wechat-miniprogram/minigame-api-typings/raw/refs/heads/master/types/wx/lib.wx.api.d.ts)

开放数据域不是宾客数据库：好友／群开放数据接口有专属运行域和授权入口限制，不能承担请柬、席位、祝福或苏七关系持久化；首轮无需启用。使用现有HTTPS后端即可，不必为迁移同时强制更换成云开发；若选云开发，也需真实环境与服务端权限，不保留浏览器相对`/api/*`假设。[微信官方小游戏示例](https://github.com/wechat-miniprogram/minigame-demo)、[示例云开发说明](https://github.com/wechat-miniprogram/minigame-demo/blob/master/CLOUD_README.md)
