## 测试怎么跑

### 基本流程

1. `git worktree add /tmp/<名字> <01给的commit hash>`——**永远在独立 worktree 里测，绝不在共享工作区跑**（02 常年有没提交的改动，你的沙盒权限本身也会挡住往共享工作区写）
2. **全新 worktree 第一步先跑一遍**（这台机器约 1 分钟，省掉大量"到底是不是真 bug"的排查）：
   ```
   Godot --headless --editor --quit-after 60 --path .
   ```
   不跑这一步，贴图、字体没走完 Godot 的资源导入，测试会读到空值：报假的"不行"，或者某个 `test_*.gd` 卡住不退出（症状：CPU 占用很低、进程一直不结束——是脚本内部跑出一个没 catch 的 SCRIPT ERROR 后再也走不到自己的 `quit()`，不是真的死循环）
3. 跑 01 点名的新 `test_*.gd`、加上直接相关/相邻的测试文件（不用每次都跑全部 20 多个文件——挑跟这次改动同一块画布、或者进出口相连的画布）
4. 针对 01 点名的重点，**自己另外写补充对抗测试**（`tools/tmp_*.gd`，跑完删掉，不提交），别只信实现者自己写的那条断言。方法论见下一节
5. 用 `godot/capture.sh <目录> <shot名...>` 截图，**自己独立截一遍**，别直接用 02 回执里现成的截图路径——那是他们自己环境下截的，自己截一遍是再核一次代码到截图这条链路本身没问题
6. 写 `godot/回执/<功能>-测试.md`（或 `比例量尺-<场景>.md` 这类）
7. **提交回执文件**：`git add -- <路径...>` 然后 `git commit -m "…" -- <路径...>`（永远带 `Co-Authored-By: Claude Sonnet 5 <noreply@anthropic.com>`），**只带自己这次的文件**（回执、标图、框 JSON 这类，不带截图以外任何代码或配置）。**10/2 更新**：这一步直接在共享工作区 `苏七镇奇缘-claude 总文件` 里做（path-limited `git add -- 具体路径`，不要 `git add -A`、不要 `git commit -a`），不用再走"worktree 提交→给 01 hash→01 落地"那一套——这一整段时间（55 桌摆位/效果图/南北背景/厨房独立测试）都是这么直接提交的，没出过问题，比旧流程省一道手续。**worktree 还是要用，但只用来跑 Godot 测试**（导入、跑 `test_*.gd`、起窗口量帧率），测完在 worktree 里看结果、写完回执再去共享工作区提交；如果共享工作区当时有 02 没提交的改动也不影响，因为你只 `add` 自己那几个路径
8. 发 `SendMessage` 给 01 一份摘要（先 `ListAgents` 确认现在在线的 01 叫什么名字——**这个名字会变**，窗口换了名字也会换，按输出里显示的名字发，不要用记忆里的旧名字）

### 补充对抗测试怎么写——几条测出来的方法论

**镜头/画布尺寸类**：别靠肉眼看截图。拿 `Camera2D` 自己的 `limit_top/bottom/left/right` + `position` + `zoom` 三样，照引擎自己夹取可见范围的算法（中心先按 limit 夹住，再按 viewport 半宽半高展开）反算出"镜头实际能看见的世界范围"，跟画布边界数字比对。这样能测出"露没露出画布外""到了边界会不会跳"这类问题，不用真的渲染画面。

**时钟/计时器类玩法**（熟了不叠、冷却、每日重置这些）：
- 不能只测"经过了多久"这种相对量，还要**直接把 now() 设成绝对的极端值**（比如跳到 2099 年），确认封顶逻辑不会因为绝对值太大就溢出/出错
- 时钟**往回调**要测：回调的量比"已经过去的时间"还小（不该触发任何纠偏逻辑，应该看到自然的部分进度，不是被莫名清零）；多轮"回调→正常前进→再回调"的恢复情况；纠偏机制自己的边界条件（比如判断条件是不是 `>` 还是 `>=`）
- 有些代码自带的"测试用改时间"钩子（比如 `fake_now`）**可能有隐藏的哨兵值限制**（吃过一次亏：`fake_now > 0.0` 才生效，传 0 或负数会静默退回真实系统时钟，测出来的根本不是你以为在测的场景）——用之前先看一眼这个钩子自己的判断条件

**证明"没有某个后门/加速口子"这种否定性结论**：光测实现者自己写的那条断言不够。要（1）扫一批可疑的方法名/字段名（`speed_up`、`instant_xxx`、`skip`、`cheat`、`debug_xxx` 这类），（2）**直接读源码**，确认关键计算路径里压根没有 `is_debug`/`debug_override` 这类分支字样——这样才能说"不只是没被这几个猜的名字测到，是代码里根本没有这条路"

**存档损坏/边界**：文件不存在、非法 JSON、顶层类型不对（数组冒充字典）、字段类型不对（该数字的给字符串/null/嵌套字典）、老版本存档字段缺失时的兼容、运行中途被外部删除——这几类挨个测一遍，正常应该都不崩、退回安全默认值。**GDScript 的 `float()` 转换对字符串有兜底（转成0.0），但对 `null` 和字典没有兜底，会报 `Invalid call. Nonexistent 'float' constructor`**——这个错不一定崩整个脚本（可能跳过继续跑），但会打日志，读存档相关代码如果没做类型判断，记得测一下这种情况。

**核对实现是否符合蓝图**：只标真正的文字冲突；蓝图没写清楚、或者实现者自己已经在回执里说明理由的灰盒决定，不用重复"发现"一遍——写"跟 XX 核对一致"就行，别制造没有的分歧。

### 最容易踩的坑——自己的测试方法出问题，别当成代码 bug

写补充测试时，撞见"失败"先别急着写进报告，**先怀疑是不是自己的测试没照真实代码路径来**。踩过的几个坑，供参考：

- 造座位、金币这类"服务端权威"的状态时，**别直接改底层字段糊弄过去**（比如 `hall.apply_change()` 硬摆一个座位、`games_save.coins` 直接赋值）。这类状态在真实代码路径里会被"服务端"（哪怕是电脑上的假数据）在下一次相关操作时用权威数据覆盖——比如金币要走 `clear_level()`/`give_gift()` 这类函数才会标记"本机有没同步的改动"（`dirty`），不标记的话下一次假的 `enterHall`/`saveProfile` 一来就把你摆的值冲掉，测出来的不是 bug，是你摆状态的方式跟真实玩家能走到的路径不一致
- 测"走到某个房间最北/最南"这类边界时，**用房间真正的几何边界（walk 多边形的边），别用某个交互点的中心坐标**——交互点半径是触发范围，不是房间墙壁，拿交互点当"最北"会测出一个不存在的"没顶到边"的假象
- 一个函数如果是"按种类一起处理"（比如 `harvest(kind)` 一次收某种果子全部熟了的地），别拿它的返回值去验证"单独一块地"的状态——想验证单块地，直接查那块地自己的状态量，不要通过一个批量操作的副作用去反推
- **自己写的探针脚本里，别用函数局部 `var` 给 signal 的 lambda 当计数器**（比如 `var coins := 0; sig.connect(func(n): coins += n)`）——GDScript 的匿名函数捕获外层局部变量时**改的是闭包自己那份拷贝，不是外层那个变量**，外面读到的 `coins` 永远是初值，而且不会报错，测试会"安静地全过"（因为两边读到的都是冻住的同一个假值，字面比较照样相等）。吃过一次亏：10/1 测厨房金币防重复，写了 `var coins5 := 0` 结果所有"发了钱"的断言全部静默失败。**改法**：计数器用 `var box := [0]`（数组按引用改）或者干脆把计数器提成脚本的成员变量（`var coins := 0` 写在 `extends SceneTree` 下面、函数外头，GPT 自己的测试脚本就是这么写的，等于隐式 `self.coins`，这样改没问题）
