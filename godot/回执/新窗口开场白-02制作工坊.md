## 五、两个出图工具怎么用（01 点名要写进文件）

### 导数据：`tools/dump_canvas.gd`

```
/Applications/Godot.app/Contents/MacOS/Godot --headless --path . --script res://tools/dump_canvas.gd -- 输出目录
```

六块各出一个 json：画布尺寸、格子大小、**游戏正在用的走路格子**（`cfg["walk_grid"]`，一行一个字符串，`1` 是能走）、交互点、落点。

- **一定要导 `walk_grid`，别照着 layout.json 重算**。重算出来的图会和游戏不一致，美术就会画出「看着能走其实撞墙」的路
- 早先我试过逐格问 `_free()`，1536×1280 要跑十几分钟；`walk_grid` 是现成的，秒出
- 宴会厅（`layered_hall.gd`）没有 `points`、`SPAWN` 这两样，代码里用 `cv.get("points")` 取，取不到就空着——别直接点属性，会报错中断

### 画图：`tools/make_ref_map.py`

```
python3 tools/make_ref_map.py 截图目录 json目录 输出目录
```

底图用 `capture.sh` 出的整张俯视（`RES=1536x1024 ./capture.sh 目录 court_overview` 这种，湖边果园用 `1536x1280`）。

**画法参数**（都在文件头上，改这几个就行）：

| 参数 | 值 | 为什么 |
| --- | --- | --- |
| `DIM` | 0.72 | 不能走的地方去色后压到七成暗。再暗底图细节就看不清了，再亮和能走的地方分不开 |
| `HATCH_GAP` | 16 | 红斜线隔多远 |
| `BLOCK` | `(232, 62, 48)` | 斜线和描边的红 |
| 描边 | `FIND_EDGES` + `MaxFilter(5)` | 能走／不能走交界画一圈红，是最好认的那层 |
| `VER` | `"v2"` | 改版加版本号（目录说明的规矩） |

**为什么是「去色压暗＋斜线＋描边」不是「盖一层红」**（01 9/20 让改的）：
v1 盖淡红，压在湖面（蓝紫）上读成紫湖、压在草莓垄（棕红）上根本看不出来。
「能走的涂淡绿」也不行——六块里四块底色本来就是绿的。**去色压暗不靠颜色分**，底色什么颜色都成立。

标签会自己避让：先试点的上下左右，撞了往外挪，**碰到画布边往里翻**（绝不越界），交互圈本身也算占位，被挤远了牵一条细线回去。

> 一处小出入：交付出去的那六张 v2 是**图例还没提「红描边」那一版**（01 9/20 提的，说下次带上，我只改了工具没重出图）。你再跑一次工具，图例会多一句「不能走（压暗＋斜线，红边是交界）」，这是对的，不是你改坏了。

## 六、最容易踩的坑

1. **导出用 zsh 不用 bash**（01 交代）
2. **提交只用 `git commit -m … -- <路径>`**，别 `git add .`——这个仓库同时有 01、03 在动，提交前先 `git diff --cached --name-only` 看一眼
3. **新 worktree 里先跑一遍** `Godot --headless --editor --quit-after 60 --path .` 把资源导完再测，不然会报假「不行」，甚至卡住不退出
4. **截图卡住多半是编译没过**：`capture.sh` 一张图开一个窗口等它自己退，脚本编译不过它就一直杵着。先 headless 跑一遍任意测试确认能编译，再去截图
5. **GDScript 几个真咬过人的**：
   - `var x := 没类型的引用.方法()` 推不出类型，编译就挂（`save`、`m.orchard` 这种都没类型）。写成 `var x: int = …`
   - `int(null)` 直接脚本报错
   - **json 里的数字读进来是小数**：`12 in [12.0]` 是 **false**，挨个 `int()` 比
   - `get_image()` 在微信里禁用；`Image.create_empty` + `ImageTexture.create_from_image` 可以
6. **测试里拨时间**：`fake_now` 要用真实纪元的量级（1_800_000_000 这种）。用 100 万那种小数字，往回拨一个月就成负数，`now()` 会掉回真实时钟，测试结果全乱
7. **界面的 `sync()` 要在 `main._process` 里叫**：测试是手动 `tick()` 的，`Control._process` 不会自己跑（湖边长凳、果园按钮都踩过）
8. **到了站的点离那块画布的出口至少 48 像素**（01 9/19 定），不然一进去就被出口圈住、来回弹。蓝图给的落点经常不够，要往里挪，挪了写进回执第二节
9. **包体量法**：整包导出要下引擎模板、这台机器下不下来。用 `--export-pack "小游戏" 临时路径/x.pck`（会写成 `x.bin`），**并且在上一个提交上用同样办法导一份当底**，两个数同一种量法才可比
10. **别碰 `../wechat-build`**

## 七、和 01 定过的规矩（不用再问）

- **回执第二节必须有数字对照表**，两列写成「蓝图值（作废）」和「**实际值（出图照这列）**」，加一列「为什么」。那张表是出图任务卡的依据，美术照「实际值」那列画，不能让人读成建议值
- **新写的字一律标「等阿鱼定」**，写进回执的表里，01 会收进 `等阿鱼定的字.md`。字都放在各画布的 `assets/*/lines.json`，改文案不改代码
- **记忆点不代写**（《世界观》4.2）：湖边亭子那句、每种果第一次收成那两句，都是阿鱼的记忆，显示「【待补】」等他写。可以给他出几个帮他回想的问题，但别拟草稿
- **数值表、季节表这类写进 json**，改数不改代码；蓝图标「待验证」的数字照抄并保留标记，别自己去查
- **做完写回执 + 分段提交 + 报 01 转 03**，回执里写清「还没上真机」「要不要部署」
