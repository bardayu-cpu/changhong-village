## 四、时间

`test_relatives.gd` 里已经测了 11:59/12:00/13:59/14:00、17:00/18:59（近似值，喂的是 11.99/13.99 这类小数）和两个 UTC 换算点，全过。**我另外写了一个独立探针**（`tools/probe_time.gd`，只在这次跑用，没有提交），把 01 点名的 8 个点**喂精确小数**（11+59/60 这样）验一遍，又从「UTC 秒 → `Relatives.beijing_hour()` → `Relatives.in_feast()`」整条链路各测一遍：

| 北京时间点 | 该不该开席 | 结果 |
| --- | --- | --- |
| 11:59 | 不 | 对 |
| 12:00 | 是 | 对 |
| 13:59 | 是 | 对 |
| 14:00 | 不 | 对 |
| 16:59 | 不 | 对 |
| 17:00 | 是 | 对 |
| 18:59 | 是 | 对 |
| 19:00 | 不 | 对 |

8 个点、两种测法（直接喂小时／走完整 UTC 链路）**全部一致，没有一个不对**。

**手机时区改了会不会有影响**：代码审查——`_feast_now()` 只用 `Time.get_unix_time_from_system()`（Godot 文档：返回 UTC 纪元秒，不受本机时区设置影响）加一个写死的 `tz_hours=8`，全仓库搜过 `relatives.gd`、`main.gd`，判开席这条路上没有调用任何和「本地时区」有关的函数（`main.gd` 里唯一一处 `get_datetime_string_from_system()` 是聊天记录时间戳，跟开席判断无关）。**架构上就不会受手机时区影响**，没有另外去改测试机的系统时区验证（改系统时区影响面大，这条靠代码审查加单元级别的数值验证已经够确定）。
