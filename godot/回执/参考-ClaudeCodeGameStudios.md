> **怎么看的**：没有 git clone。下载文件按 HANDOFF §0.6 要阿鱼在 02 窗口亲口点头，01 转的不算。这次在 GitHub 网页上逐个读了 7 个文件：
> - asset-spec、art-bible、smoke-check、story-done、test-evidence-review 五个 skill；
> - validate-assets.sh、validate-commit.sh 两个 hook。
>
> 它是一整套「49 个 AI 角色 + 70 多个命令」的工作室模板，很重。我们只挑跟画面、图、截图相关的几小块。

## 一句话结论

| | 能用吗 | 一句话 |
|---|---|---|
| 1a 零件规格 asset-spec | **能用，挑 4 个字段** | 给 GPT 的零件清单补上「编号、状态、一句话样子、依哪条规矩」，再加一张总表 |
| 1b 画风圣经 art-bible | **能用它的目录** | 我们的画风规矩散在五六个地方，照它的 9 节目录收成一页；内容 GPT 起草、阿鱼拍板 |
| 2 提交时自动检查 hooks | **思路能用，脚本不用** | 它只查文件名和 JSON 写错，不查图。我们自己写一个提交前检查：JSON、图的尺寸、透明 0/255、图多大 |
| 3 截图才算完 QA evidence | **规矩能用三条，整套不用** | 补上：截图标明是哪一版的、「没验成」单列不算过、新加一屏就带一个截图预设 |

## 1. 零件规格、画风圣经

### 1a. asset-spec（零件规格）

**它每件零件写这些**：
- 编号（ASSET-001 起，跨场景不重复）、名字、类别、尺寸、格式、命名；
- 两三句话的样子描述；
- 依画风圣经哪几条；
- 给 AI 出图的提示词；
- 状态（要做 → 在做 → 做完 → 批准）。

所有场景的零件再汇成一张总表，数得出做了几件、差几件。

**我们现在的**（`claude-给GPT的待办.md`、`claude-给GPT-造景台升级的目的.md`、ASSETS §15）：
- 每件有文件名、画什么、「尺寸照原图」、透明底硬边不带字；
- 比例按 §15 人 = 1 表；
- 摆在哪由造景台的摆放清单给（02 已经提了要补脚点、占地、座位那几样，见 `回执/造景台摆放清单-格式建议.md`）。

**值得补的 4 样**：
1. **编号**：每件一个不变的编号（比如 `B55-T01` 桌子、`B55-P01` 路引）。现在靠文件名认，文件名一升版（v1 → v2）就对不上历史；交接单、摆放清单、回执都写编号，查起来一条线。
2. **状态**：要画 → 交了 → 02 核过（尺寸、透明、比例）→ 阿鱼点头 → 进游戏。现在待办表只有「待做 / 交了」，交了以后有没有核、阿鱼看没看，要翻聊天记录。
3. **一两句「长什么样」**：现在写「照原图的样子」。原图一换（9/30 就换过两次），零件该长什么样就没了依据。
4. **依哪条规矩**：比如「比例 §15 宴会圆桌行」「新人照参考图」「图上不叠字」。打回的时候说得出是违反了哪条。

**一张总表**：所有场景的零件一张表（编号、文件、状态、多大、在哪些场景用）。顺带能看出哪些零件好几个场景在共用。

**不用的**：
- 「出图提示词」那栏：GPT 自己画，提示词是它的事；
- 3D 面数那些：我们是 2D 像素画。

**工作量**：
- 01 改给 GPT 的模板：半小时；
- 02 把现有零件补编号、建总表：1～2 小时；
- 以后每批交接顺手维护。

### 1b. art-bible（画风圣经）

**它分 9 节**：
1. 一句话视觉规矩；
2. 气氛；
3. 形状语言；
4. 配色（5～7 个主色，每个颜色代表什么）；
5. 人物设计方向；
6. 场景设计语言；
7. 界面方向（字体、图标、要不要叠字）；
8. 素材硬规格（格式、命名、尺寸档位、包体上限）；
9. 参考图（学它哪几处、避开哪几处）。

**我们现在的规矩散在**：ASSETS.md（格式、§15 比例）、HANDOFF §0（新人形象、地名）、给 GPT 的待办（像素画、斜俯视、硬边、不叠字）、02 的备忘（图上不叠字、底图最底层是地砖）、各次阿鱼的话（「乱糟糟」「这大概是我想要的」）。GPT 每次接活要自己拼这些，常漏一条。

**能用的是它的目录**。照这 9 节收成一页《罗曼山庄画风》：
- 第 7 节放「图上不叠字」；
- 第 8 节放 §15 比例、主包 4 MB、透明 0/255 规矩（界面底和特效可以半透明，01 D 9/30 定）；
- 第 9 节放阿鱼点过头的那张现场效果图、新人参考图，写清「学哪里」「别学哪里」（比如 9/30 阿鱼嫌乱的那几种铺法）。

**谁写**：按 HANDOFF §0.7，画面由 GPT 出方案、阿鱼拍板。02 只把已经定了的规矩按目录摆好、标出处。没定的（配色代表什么、气氛词）留「待讨论」，给 GPT 起草。

**工作量**：02 收拢已定的规矩 2～3 小时；GPT 起草空着的几节、阿鱼看一遍。

## 2. 提交时自动检查（hooks）

**它的两个脚本实际查什么**：
- `validate-assets.sh`：Claude 写了 `assets/` 下的文件以后跑。文件名有大写、空格、连字符就提醒；`data/` 下的 JSON 读不出来就报错。**不看图**：不查尺寸、不查透明、不查多大。
- `validate-commit.sh`：Claude 要 `git commit` 时跑。
  - JSON 写错就拦下；
  - 设计文档缺规定的章节、代码里写死数值、TODO 没写是谁的，只提醒。

两个都是 **Claude Code 的钩子**（挂在 Claude 写文件、跑命令那一步），不是 git 自己的钩子。

**能搬来的只有「JSON 写错拦下」这一条**，别的要我们自己写。我们最需要查的是图，它没有。

**我们的版本（建议）：一个 git 提交前检查**
- 写一个 `godot/tools/check_assets.py`，查**这次要提交的**文件：
  1. **JSON 能不能读**：scene.json、layout.json、ambience、minigames.json、厨房的 atlas_regions.json。读不出来拦下。
  2. **场景零件的透明只能 0 或 255**（`blk_*`、`art_*` 这类）：有半透明边就拦下。界面底、特效（`base_ui_*`、`decal_*`）照 01 9/30 的规矩放行。
  3. **尺寸对得上**：瓦片照 `回执/宴会厅55桌-瓦片规格.md` 的尺寸；底图照场景画布大小（1536 宽）。对不上拦下。
  4. **图有多大**：单张超过 1 MB、或这次提交让 `assets/` 一下子多出 2 MB 以上，提醒。厨房 v1 那三张图就是这么把游戏内容翻了一倍。
  5. 文件名带空格、大写只提醒（我们 `assets/` 下本来就是小写下划线）。
- **接到 git**：脚本放 `godot/tools/githooks/pre-commit`，仓库里跑一次 `git config core.hooksPath godot/tools/githooks`，以后 01、02、03、04 哪个窗口提交都会过一遍。不用 Claude Code 钩子：那样只管装了钩子的那个窗口。
  - 这一步改的是本仓库的 git 设置，装之前 01 定一下。
- **GPT 交的图**也过同一个脚本：02 盯交接文件夹那一步（`gpt_inbox.py`）顺手跑，交来就知道哪张不合格，不用等进仓库。
- 我们已经有的：
  - `check_blocks.py`（积木摊开看）、`scale_check.py`（比例量尺）、`check_tile.py`（瓦片接缝）。这些是人看着用的，**不放进提交检查**：太慢，而且要人判断。
  - 提交检查只放「不用判断、对就是对」的那几条。

**不用的**：
- 「代码里写死数值」：我们的难度、金币早就放在 json 里；
- 「TODO 要写是谁的」：我们的「待讨论」「TBD」是阿鱼故意留的，按规矩不许删，查它反而添乱。
- 「设计文档缺章节」可以以后再说。CLAUDE.md 要求每个功能模块有用户故事、功能需求、交互说明、异常处理，可以做成只提醒的一条，但改文档本来就要阿鱼先确认，优先级低。

**工作量**：
- 02 写脚本 + 测试（拿几张故意做坏的图、坏 JSON 测它拦不拦）：半天；
- 接 git、接 gpt_inbox：半小时。

## 3. 「改了看得见的东西，必须开游戏截图才算完」

**它的规矩**（story-done、smoke-check、test-evidence-review）：
- 改了玩家看得见的东西，每个改到的画面都要**开游戏截一张图留下来**，存进固定的文件夹，才算做完；
- 「我看了，没问题」这种话**不算证据**；
- 截图记录要写：哪天、哪一版、什么设备 / 分辨率、谁看的；
- 比这一轮开工还早的截图，算**过期**；
- 「没验成」（没开游戏、没跑测试）单列成一档，**排在「过了」下面**，不能当过了交出去；
- 交给测试的人之前，先跑一遍「冒烟检查」：测试全跑、游戏开起来、按清单点一遍。

**我们现在的**：
- 03 跑测试、04 按客人视角复看（540×960、长屏 1170×2532）；
- 截图预设 `--shot=` 一键截；
- 回执里写截图路径；
- 出码前：导入 grep 0、测试全过、桥测试。

大方向一样，而且我们在手机竖屏这块比它细。

**缺的三条，值得补**：
1. **截图要标明是哪一版的。**
   - 现在 `回执/` 里的截图名字是「55桌v9-台前.png」，看不出是哪个提交截的。
   - 这次 04 就拿到过一张早一轮的图来判「被切」：判到最后，那张图里其实没切，是边框贴边。
   - 补法：截图文件名带提交号（`55桌-台前-4589c0e.png`），或者回执里每张图后面写「提交 xxx、540×960、预设 big_stage」。04 复看先对一下提交号，不对就重截。
2. **「没验成」单列，不算过。**
   - 现在回执的「风险」里会写「真机没验」，但跟别的风险混在一起。
   - 厨房 v1.1 的前后台暂停就是这样：电脑上测过，真机没测，很容易被读成「做完了」。
   - 补法：回执固定三档——**验过 / 没验成（为什么、谁去验）/ 不适用**；「没验成」不清零，就不出码给阿鱼。
3. **新加一屏，同一个提交里带一个截图预设。**
   - 厨房 v1 进来时只有「开始页」能一键截，炒菜那屏、结算卡要 04 专门要了我才补。
   - 补法：做了新画面、新弹窗、新状态，就在 `main.gd` 的 `_setup_shot` 里加一个预设，跟功能一起提交；03、04 拿到就能截。

**可以顺手做的一个小工具**：`tools/smoke_shots.sh`。
- 一条命令，把一串固定预设按 540×960 和 1170×2532 各截一遍，拼成一张总览图，角上印提交号；
- 出码前跑一遍，01 一眼看完所有画面有没有坏；
- 工作量约半天。

**不用的**：它那套冲刺、故事卡、签字表（一项项打勾的批准行），我们四个窗口 + 阿鱼，用不上这么重的流程。

## 建议先做哪几样（01 定）

| 顺序 | 做什么 | 谁 | 大概多久 |
|---|---|---|---|
| 1 | 提交前检查脚本（JSON、透明 0/255、尺寸、图多大），接 git 和 gpt_inbox | 02 | 半天 |
| 2 | 回执三档（验过 / 没验成 / 不适用）+ 截图标提交号 | 01 定规矩，大家照写 | 当天 |
| 3 | 给 GPT 的零件清单补编号、状态、一句话样子、依哪条规矩 + 总表 | 01 改模板，02 补现有的 | 2 小时 |
| 4 | 新画面带截图预设（写进规矩）+ smoke_shots.sh | 02 | 半天 |
| 5 | 《罗曼山庄画风》一页，照它的 9 节目录 | 02 收已定的，GPT 起草空的，阿鱼拍板 | 2～3 小时 + GPT |

都没动工程，等 01 和阿鱼定了再做。
