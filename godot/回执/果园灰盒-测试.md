## 三、本机存档/日期的边界——自己另外写的补充测试

`test_orchard.gd` 测了摘一颗、今天摘过按钮收、隔天能再摘这条主线，但 01 点名的几个更刁钻的情形（同一天反复进出、时钟往回调、存档损坏、存档被删）没有专门覆盖。补写了 `tmp_orchard_save_edge.gd`（直接用 `OrchardSave`，跑完删了），6 组全过：

1. 正常跨天：没摘过是空串，摘了记下那天，隔天日期不等于摘的那天（能再摘）
2. 同一天反复读存档（模拟反复进出画布）：记录还在，不会因为重新读盘就丢
3. 时钟往回调：摘的时候记的是 12/10，把系统时间往回调到 12/08 再查，`picked_on == 12/08` 判定为 false——**也就是说把系统时间往回调，是能让"今天已摘过"重新变成"没摘过"的**。这条已经在回执第五节写明"本机记，不上服务器、没有作弊面"，是设计上就没打算防的边界，不算新发现的 bug，写在这里是为了确认这条边界确实符合设计预期
4. 存档文件内容损坏（不是合法 JSON）：`load_local()` 内部会打一条引擎级的 JSON 解析错误日志（控制台能看见 `ERROR:` 字样），但脚本本身不崩、不抛异常，退回"没摘过"这个宽松默认值——这条日志是 Godot 自带 JSON 解析器的正常提示，不是脚本崩溃，怕误认成新 bug 特地记一笔
5. 合法 JSON 但结构不对（`picked` 字段是数组不是字典）：同样不崩，退回没摘过
6. 存档文件中途被外部删掉：内存里的 `save` 对象在本次运行里还记得（不会平白丢数据）；只有换一个新对象重新读盘（相当于重启小游戏或清缓存）才会因为文件不存在退回没摘过
